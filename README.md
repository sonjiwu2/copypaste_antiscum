# 🛡️ АНТИСКАМ ТРЕНАЖЁР

**Интерактивный тренажёр по распознаванию мошенничества в сделках на классифайдах.**
Кейс 5 «Антискам тренажёр», Avito Start.

Пользователь выбирает роль покупателя или продавца, попадает в реалистичную переписку
с мошенником, принимает решения на развилках и сразу видит последствия каждого шага —
не «правильно/неправильно», а какой именно красный флаг он пропустил и как надо было
поступить. Это ветвящийся сценарий, где следующий шаг решает сервер, а не тест с
очевидными вариантами.

## 1. Геймплей

### Путь пользователя

```text
роль → каталог → запуск попытки → диалог → решение → последствие
     → следующий узел → … → финал → оценка → разбор → прогресс
```

Путь реализован целиком, от старта до сохранённого в PostgreSQL результата.

### Экраны

| Маршрут | Что там |
|---|---|
| `/` | Баннер, выбор роли, карточки-утилиты, рекомендованные миссии |
| `/missions` | Каталог из 14 миссий, фильтры, сортировка |
| `/mission/:id` | Переписка, варианты действия, панель разбора |
| `/progress` | Уровень, статистика, достижения, таблица пройденных |
| `/weekly-test` | ИИ-экзамен: 20 вопросов, таймер, 3 жизни |
| `/rewards` · `/rules` · `/settings` | Ежедневная награда · обучение · настройки |

### Как устроен диалог

Сценарий — **граф узлов**: `message` (реплика собеседника или системное событие),
`decision` (развилка с вариантами), `terminal` (финал ветки с итогом `safe`/`unsafe`).
Отправитель бывает `buyer`, `seller` или `system` — системный текст показывается
отдельной хроникой событий, а не сообщением в ленте.

Реплики игрока не пишутся вручную: у каждого варианта есть закреплённый `playerReply`,
который после выбора попадает в переписку. Диалог остаётся реалистичным, а граф —
детерминированным.

**Сервер не отдаёт клиенту** полный граф, будущие ветки, `nextNodeId` до выбора
и правильный ответ теста до отправки результата. Клиент присылает только `nodeId`,
`choiceId` и `idempotencyKey` — всё остальное вычисляет сервер. Пройти сценарий
«наперёд» через DevTools невозможно.

После каждого решения приходит `consequence`: `severity` (`safe`/`warning`/`dangerous`),
что произошло, какой признак был красным флагом и какое правило безопасности здесь работает.

### Фильтры каталога

Роль · Сложность · Тип мошенничества (6 категорий) · Состояние прохождения,
плюс сортировка по рекомендации / сложности / XP / названию. У каждого фильтра —
счётчик подходящих миссий. Роль читается ещё и из адреса (`?role=buyer`), поэтому
присланная ссылка показывает именно то, что в ней написано.

### XP и прогресс

| Механика | Значение |
|---|---|
| Базовый XP миссии | `easy` 10 · `medium` 15 · `hard` 20 |
| Начисление | `max(10, round(базовый × результат / 100))`, при повторе — **только прирост** |
| Уровень | `floor(общий XP / 100) + 1` |
| Ежедневная награда | +25 XP раз в сутки |
| ИИ-экзамен | +100 XP только при сдаче |
| Серия | растёт день за днём, пропуск обнуляет |
| Достижения | 4 бейджа: первая миссия · 5 миссий · 100 % результат · серия 3 дня |

**Разделение данных:** сервер (`GET /api/v1/progress`) считает статистику по сохранённым
попыткам — завершённые попытки, средний/лучший/последний балл, прогресс по сценариям,
слабые risk-теги, рекомендации. Браузер (`localStorage`) хранит только геймификацию:
XP, уровень, серию, бейджи.

### Что реализовано, а что — заготовка

| ✅ Работает полностью | 🚧 В разработке |
|---|---|
| Каталог, фильтры, сортировка | **АНТИСКАМ SOS** — карточка на главной помечена «В РАЗРАБОТКЕ», по нажатию показывает подсказку. Пошагового плана действий пока нет |
| Прохождение, последствия, финал | Таблица лидеров — заглушка «СКОРО», нужны аккаунты и общий сервер |
| Оценка и сохранение в PostgreSQL | Магазин наград: реализована только ежедневная награда, бейджи — на странице прогресса |
| Серверная статистика прохождений | Анимации UI, масштаб интерфейса, высокая контрастность — три строки настроек помечены «В разработке» |
| XP, уровень, серия, 4 достижения | |
| ИИ-экзамен на 20 вопросов | |
| Настройки, сброс прогресса, тема, звук | |

## 3. Еженедельный ИИ-экзамен

Отдельный режим на `/weekly-test` поверх сценариев.

| Параметр | Значение |
|---|---|
| Вопросов | 20 |
| Время | 10 минут |
| Жизней | 3 (третья ошибка завершает экзамен) |
| Порог сдачи | 18 из 20 |
| Награда | 100 XP только при сдаче |
| Следующая попытка | через 7 суток после завершения |

**Ход экзамена.** `POST /weekly-tests/current` возвращает активный тест либо **один раз**
создаёт новый — обновление страницы не тратит лимит ИИ. Каждый ответ проверяется отдельно
через `/answer`, который отвечает только `{"correct": true|false}`: индекс правильного
варианта не раскрывается. `/submit` пересчитывает всё заново на сервере и сохраняет результат
идемпотентно. Экран результата показывает балл, разбор каждого вопроса и таймер до следующего теста.

Черновик (вопрос, ответы, жизни) лежит в `localStorage`, поэтому случайное обновление
страницы не обнуляет прогресс. Таймер привязан к серверному `expiresAt`, а не к вкладке.

### Выбор провайдера

```text
GROQ_API_KEY задан? ──ДА──→ Groq Cloud (openai/gpt-oss-20b)  → source: "groq"
        │
        НЕТ → XAI_API_KEY задан? ──ДА──→ xAI Grok (grok-4.3) → source: "grok"
                      │
                      НЕТ ──────────────→ встроенный резерв   → source: "fallback"
```

Резерв включается **автоматически** и при наличии ключа: провайдер вернул ошибку
или таймаут, исчерпан лимит, либо ответ модели не прошёл доменную валидацию
(не 20 вопросов, не 4 варианта, повтор вариантов, пустое объяснение). Приложение
никогда не падает из-за недоступности ИИ. Источник виден пользователю прямо в интерфейсе.

**xAI/Grok — необязательный второй провайдер.** Включается, только если `GROQ_API_KEY`
пуст, а `XAI_API_KEY` задан. Groq выбран основным из-за бесплатного тарифа.

### Что уходит в ИИ

**Ничего пользовательского.** Тип контекста генерации пустой по замыслу:

```go
// GenerationContext намеренно не содержит данные профиля или историю:
// сторонний API получает только общую инструкцию создать учебный тест.
type GenerationContext struct{}
```

Ни cookie, ни идентификатор профиля, ни история прохождений не передаются. Ответ модели
загоняется в строгую JSON-схему (`response_format: json_schema`, `strict: true`) и затем
проверяется доменной валидацией. Ошибки Groq логируются без заголовка `Authorization`
и без текста запроса.

### 🔐 Правила обращения с ключом

> - Ключ читает **только backend**, из переменной окружения.
> - ❌ Не помещать во frontend. Переменной `VITE_GROQ_API_KEY` **не существует и не должно** —
>   всё с префиксом `VITE_` Vite вшивает в JS-бандл и отдаёт браузеру.
> - ❌ Не записывать в Docker-образ, `Dockerfile`, `compose.yaml` или Git.
> - ✅ Локально — только в `.env` (исключён из Git). На Render — только в Environment
>   Variables сервиса **backend**.

**Хранение теста.** При `STORAGE_DRIVER=postgres` тест переживает перезапуск и отсчёт
7 суток работает корректно. При `STORAGE_DRIVER=memory` тест исчезнет после перезапуска,
и следующий запрос снова потратит лимит ИИ. Нужны миграции `00005`–`00007`.

## 4. Архитектура

```text
                    Browser
                       │ HTTPS
                       ▼
        ┌──────────────────────────────┐
        │  Frontend (nginx)             │
        │  статика SPA + proxy /api     │
        └──────────────┬───────────────┘
                       ▼
        ┌──────────────────────────────┐
        │  Go Backend :8080             │
        │  handler → service → domain   │
        │           → repository        │
        └───┬───────────┬───────────┬──┘
            ▼           ▼           ▼
    ┌────────────┐ ┌──────────┐ ┌──────────────┐
    │ PostgreSQL │ │  JSON-   │ │  Groq API    │
    │ профили    │ │ сценарии │ │      ↓       │
    │ попытки    │ │ go:embed │ │  fallback-   │
    │ решения    │ │ 14 файлов│ │  генератор   │
    │ прогресс   │ └──────────┘ └──────────────┘
    │ тесты      │
    └────────────┘
```

**Почему один origin.** Nginx фронтенда проксирует `/api` на backend, поэтому браузер
видит один адрес. Следствия: cookie профиля остаётся same-site, **CORS не нужен вовсе**,
не надо ставить `SameSite=None`. Локально в Compose nginx ходит на `backend:8080` по имени
сервиса. Если фронтенд всё же на другом сайте — доступ открывается явно через
`CORS_ALLOWED_ORIGINS`; маска `*` отвергается на старте, потому что ответы привязаны
к cookie профиля.

**Слои backend:**

```text
httpapi   маршруты, DTO, middleware, перевод доменных ошибок в HTTP-коды
services  scenario · attempt · profile · progress · weeklytest
domain    правила без знания об HTTP и PostgreSQL
storage   postgres (production) / memory (явные тесты и демо без БД)
```

`domain` не импортирует `net/http` и `pgx`; `service` не знает про `http.Request`
и публичные DTO; `repository` хранит и читает, но не принимает продуктовых решений.
Нет пакетов `utils`/`helpers`/`common`, нет DI-контейнера и event bus. Единственное
место сборки зависимостей — `internal/app/application.go`.

**Frontend** организован по Feature-Sliced Design: `app` → `pages` → `widgets` →
`features` → `entities` → `shared`. Интерфейс не содержит собственной копии сценариев:
каталог, диалоги, результат и статистика приходят только из API.

## 5. Стек технологий

### Backend

| Технология | Версия | Зачем |
|---|---|---|
| **Go** | 1.25.12 | Основной язык |
| **net/http** | stdlib | Сервер и роутер. `ServeMux` в Go 1.22+ умеет паттерны вида `POST /api/v1/attempts/{attemptId}/choices`, поэтому внешний фреймворк не понадобился |
| **PostgreSQL** | 16.14 | Профили, попытки, решения, прогресс, тесты |
| **pgx/v5** | 5.10.0 | Драйвер и пул соединений |
| **goose/v3** | 3.26.0 | Миграции, встроенные в бинарник |
| **golang.org/x/sync** | 0.22.0 | `singleflight` против двойной генерации теста |
| **log/slog**, **go:embed** | stdlib | Структурные логи; сценарии и миграции внутри бинарника |
| **golangci-lint** | v2.1.6 | 13 линтеров поверх стандартного набора |

> **Почему PostgreSQL.** Данные строго реляционные: профиль → попытки → решения,
> с обязательной ссылкой попытки на конкретную **версию** сценария. Нужны транзакции,
> уникальные ограничения для идемпотентности и optimistic locking. SQLite не даёт
> нормальной конкурентности, документная БД потребовала бы поддерживать целостность вручную.

> **Почему `net/http`, а не chi.** В карте ролей значился `chi`, но стандартный `ServeMux`
> покрывает всё нужное — отказ от зависимости уменьшил поверхность обновлений и размер образа.

| **Vite** | 8.2.0 | Сборка и dev-сервер с прокси на API |
| **React Router** | 6.30 | Клиентский роутинг |
| **TanStack React Query** | 5.101 | Запросы, кэш, состояния загрузки и ошибок |
| **Zustand** | 5.0 | Сторы: настройки, прогресс, уведомления, тосты |
| **Vitest + Testing Library** | 4.1 / 16.3 | Юнит- и компонентные тесты |
| **ESLint 9 + Prettier 3** | — | Линт и форматирование |
| **nginx** | 1.27-alpine | Раздача статики и прокси в production-образе |

> **Почему нет MUI/Ant Design.** У проекта собственный пиксельный визуальный язык
> с растровыми ассетами и шрифтом Monocraft. Тянуть тяжёлую библиотеку ради компонентов,
> которые пришлось бы полностью перекрашивать, смысла не было — сделаны свои примитивы
> `PixelIcon` и `Glyph`, токены вынесены в `tokens.css`.

### Инфраструктура

Docker + Compose v2 · Docker Hub · Render · GitHub Actions · Pinggy (туннель для
демонстрации локального стенда) · OpenAPI 3.0.3.

## 7. Особенности реализации

**Идемпотентность шага.** Клиент обязан прислать `idempotencyKey`. Повтор того же запроса
возвращает сохранённый результат, а не делает второй переход; другой payload с тем же
ключом получает `409`. Гарантия на уровне БД: уникальность `(attempt_id, idempotency_key)`,
попытка и решение пишутся одной транзакцией. Двойной клик и ретрай сети не ломают прохождение.

**Optimistic locking.** У попытки есть `version`. Параллельное обновление из двух вкладок
не смешивает состояния: второй запрос получит `CONCURRENT_TRANSITION`, устаревший узел — `STALE_NODE`.

**Неизменяемый архив версий сценариев.** При старте JSON-файлы декодируются строгим
парсером, проходят доменную проверку и синхронизируются в `scenario_versions` одной
транзакцией. Пара `(scenario_id, version)` неизменяема; тот же канонический SHA-256
синхронизируется идемпотентно; **другой hash при той же версии останавливает запуск сервиса**.
Старая попытка после деплоя продолжает читать ту версию, с которой началась — иначе
незаконченное прохождение ссылалось бы на узлы, которых больше нет.

**Анонимный профиль.** Учётных записей нет. Первый запрос к `/api/v1/**` создаёт профиль
и выдаёт cookie `ast_profile` (`HttpOnly`, `SameSite=Lax`, `Path=/`). Чужая попытка отвечает
`403 ATTEMPT_FORBIDDEN`. `/healthz` и `/readyz` профиль не создают — иначе healthcheck
плодил бы по профилю каждые 10 секунд.

**Никакого тихого отката на память.** При недоступной базе приложение падает с явной
ошибкой, а не переключается на in-memory: молчаливый откат означал бы, что пользователь
проходит сценарии, а результаты исчезают при перезапуске.

**Readiness против liveness.** `/healthz` подтверждает только, что процесс жив.
`/readyz` проверяет PostgreSQL — на него ориентируются Compose и Render, поэтому
недоступная база снимает backend с готовности вместо отдачи 500 пользователям.

**Защита от двойной генерации теста.** Создание экзамена обёрнуто в `singleflight`
по ключу «профиль + дата цикла»: два одновременных запроса дадут одно обращение к Groq.

**Безопасность контейнеров.** Backend и migrate работают под UID 65532 non-root,
с `no-new-privileges` и read-only корневой ФС (запись только в tmpfs). PostgreSQL
не публикует порт на host. Миграции встроены в тот же образ, что и API, поэтому схема
не может разойтись с кодом. Секретов в образах нет.

**Ошибки наружу.** Всегда JSON `{"error": {"code", "message", "requestId"}}`, даже на
неизвестном пути. Наружу не уходят SQL-ошибки, stack trace и внутренние коэффициенты
scoring — фронтенд принимает решения по `code`, а не по тексту.

## 12. Docker и деплой на Render

### Образы

| Образ | Что внутри |
|---|---|
| **backend** | Multi-stage: Go 1.25.12-alpine → alpine 3.23.5. Бинарники `api` и `migrate`, non-root UID 65532, healthcheck `/healthz` |
| **frontend** | Multi-stage: node 22.14-alpine (`npm ci` → build) → nginx 1.27-alpine. Порт 8080, healthcheck `/index.html` |

### ⚠️ Frontend собирается в двух вариантах

`frontend/Dockerfile` принимает build-arg:

```dockerfile
ARG NGINX_CONFIG=nginx.conf
COPY ${NGINX_CONFIG} /etc/nginx/nginx.conf
```

| Вариант | Build-arg | upstream nginx | Где |
|---|---|---|---|
| Локальный | по умолчанию | `backend:8080` (имя сервиса Compose) | Docker Compose |
| Render | `NGINX_CONFIG=nginx.render.conf` | `antiscum-backend.onrender.com:443` | Render |

**Образы не взаимозаменяемы.** Если опубликовать на Render образ со сборкой по умолчанию,
nginx попытается резолвить хост `backend`, которого там нет: статика откроется,
а `/api` вернёт `502` — **приложение загрузится, но каталог миссий будет пустым.**
При переименовании backend-сервиса на Render надо править `nginx.render.conf`
и пересобирать образ: nginx резолвит upstream на старте, а не на каждый запрос.

Сборка и публикация:

```powershell
docker build -t sonjiwu/antiscum-backend:latest ./backend
```

```powershell
docker build --build-arg NGINX_CONFIG=nginx.render.conf -t sonjiwu/antiscum-frontend:latest ./frontend
```

```powershell
docker login ; docker push sonjiwu/antiscum-backend:latest ; docker push sonjiwu/antiscum-frontend:latest
```

### Как работает деплой сейчас

Оба сервиса подняты на Render из **готовых образов Docker Hub**, без сборки на стороне платформы.

```text
Пользователь ──https──→ Render: antiscum-frontend  (nginx.render.conf, :8080)
                              │  отдаёт SPA
                              │  /api, /healthz, /readyz  ──https(SNI)──→
                        Render: antiscum-backend  (Go API, :8080)
                              ├──→ PostgreSQL (managed)
                              └──→ Groq API ↓ fallback
```

Для браузера это **один origin** — `antiscum-frontend.onrender.com`. Пользователь никогда
не обращается к backend напрямую, поэтому cookie остаётся same-site и CORS на Render не нужен.
Проверить всю цепочку можно одной командой: если фронтенд отвечает `{"status":"ok"}`,
значит его nginx успешно доходит до backend.
P.S Так как данный сервис бесплатный, то происходит некоторая задержка при обработке шаблонов запроса. Именно поэтому настоятельно рекомендую, если сценарии в разделе "МИССИИ" недоступны обновлять страницу, до тех пор пока сервис не начнет работать, обычно это работает хорошо)

```powershell
curl.exe https://antiscum-frontend.onrender.com/healthz
```

**Настройки сервисов** (оба — Web Service → Deploy an existing image, порт `8080`):

| | backend | frontend |
|---|---|---|
| Образ | `sonjiwu/antiscum-backend:latest` | `sonjiwu/antiscum-frontend:latest` |
| Health Check Path | `/readyz` | `/index.html` |
| Env-переменные | `DATABASE_URL` 🔐, `STORAGE_DRIVER=postgres`, `COOKIE_SECURE=true`, `GROQ_API_KEY` 🔐, `GROQ_MODEL`, `GROQ_BASE_URL`, `GROQ_REQUEST_TIMEOUT=40s`, `HTTP_WRITE_TIMEOUT=60s` | не нужны — адрес backend зашит в образ |

`HTTP_WRITE_TIMEOUT=60s` обязателен: первая генерация экзамена Groq занимает до минуты.
`CORS_ALLOWED_ORIGINS` оставлен пустым намеренно.

**Миграции.** Образ backend содержит два бинарника, схема применяется отдельно от старта API:
`/usr/local/bin/migrate up` запускается как Pre-Deploy Command или отдельным Job перед выкаткой.

**Обновление публичной версии:** пересобрать образ → `docker push` → в Render
**Manual Deploy → Deploy latest image**.

## 15. Использование ИИ

### ИИ внутри продукта

Еженедельный экзамен генерируется **Groq Cloud** (`openai/gpt-oss-20b`), опционально —
**xAI Grok**. Технически:

- строгая JSON-схема ответа (`response_format: json_schema`, `strict: true`) — модель
  физически не может вернуть свободный текст;
- системный промпт из 14 правил задаёт критерии безопасности: правильный ответ не должен
  содержать ни одного рискованного шага, дистракторы обязаны быть реалистичными,
  `correctIndex` равномерно распределён по всем четырём позициям, модель проводит
  самопроверку каждого вопроса до отправки;
- **после** ответа модели запускается доменная валидация: ровно 20 вопросов, 4 непустых
  неповторяющихся варианта, корректный индекс, непустое объяснение. Не прошло — резервный тест;
- `temperature: 0.2`, `reasoning_effort: low` — экзамен должен быть предсказуемым, а не творческим;
- `max_completion_tokens: 6200` подобран так, чтобы весь экзамен уложился в один запрос
  и в бесплатный лимит Groq 8000 TPM: разбиение на две части резервировало лимит дважды
  и приводило к `HTTP 429`.

**Сценарии тренажёра ИИ не генерирует** — все 14 сценариев авторские, лежат в
`backend/scenarios/*.json` и проверяются валидатором графа.

### ИИ в разработке проекта

Проект разрабатывался в подходе **vibe coding**: значительная часть кода, сценарного
контента и инфраструктурных файлов написана с помощью ИИ-агентов.

| Агент | Где применялся |
|---|---|
| **Claude Code** | Основной агент: архитектура backend, движок сценариев, слой хранения, ИИ-экзамен, тесты, Docker и документация |
| **Grok** | Генерация и доработка сценарного контента, формулировки объяснений и правил безопасности |
| **Codex** | Фронтенд-компоненты, вёрстка экранов и вспомогательные скрипты |

Результаты работы агентов не принимались вслепую: каждое изменение проходило ревью
человеком перед merge, юнит- и race-тесты, PostgreSQL integration suite, Docker Compose
smoke и линтеры обеих частей. Архитектурные решения, review и merge остались за командой.

## 17. Устранение частых ошибок

**🔴 Приложение открылось, но каталог миссий пустой.** Nginx не достучался до backend:

```powershell
curl.exe -i http://localhost:3000/healthz
```

`502` локально → backend не поднялся, смотрите `docker compose logs backend`.
`502` **на Render** → образ фронтенда собран без `--build-arg NGINX_CONFIG=nginx.render.conf`
(см. раздел 12). Пересоберите и опубликуйте заново.

**🔴 `DATABASE_URL обязателен при STORAGE_DRIVER="postgres"`.** Это намеренная ошибка
конфигурации — тихого отката на память в проекте нет. Задайте `$env:DATABASE_URL`.

**🔴 `/readyz` даёт 503, `/healthz` — 200.** Процесс жив, PostgreSQL недоступен:
`docker compose ps postgres` и `docker compose logs postgres`.

**🔴 Backend не стартует, в логе конфликт hash сценария.** Содержимое JSON изменили,
не увеличив поле `version` — сработала защита архива версий. Увеличьте `version`
в изменённом файле `backend/scenarios/*.json`.

**🔴 Еженедельный тест всегда «РЕЗЕРВНЫЙ ТЕСТ».** По порядку: `GROQ_API_KEY` задан
в окружении **backend** (не фронтенда) · ключ действителен · не исчерпан лимит
(в логе будет `Groq ответил HTTP 429`) · `HTTP_WRITE_TIMEOUT` не меньше `60s` ·
после правки `.env` выполнен `docker compose up -d --build`.

**🔴 Тест пересоздаётся после каждого перезапуска.** Backend работает с
`STORAGE_DRIVER=memory`. Переключите на `postgres` и проверьте `go run ./cmd/migrate status`.

**🔴 Порт занят.**

```powershell
$env:FRONTEND_PORT='3100'; $env:BACKEND_PORT='8180'; docker compose up -d
```

**🔴 Прогресс пропал.** `docker compose down -v` удаляет volume безвозвратно; очищенная
cookie `ast_profile` означает потерю анонимной истории; в другом браузере или инкогнито
свой профиль. Обычный `docker compose down` и рестарт прогресс **не удаляют**.
